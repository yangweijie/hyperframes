## studio dev server 的 layer 导出 0xC000007B 根因修复（2026-08-17）

- 用户在 studio 点 "Export with FFmpeg"（engine=layer）报 `Failed to launch browser: Code 3221225595` (0xC000007B)。本机只有 Edge、没有 Chrome。
- 根因：用户跑预览走的是 **studio 的 vite dev server**（`packages/studio/vite.adapter.ts` → `vite.browser.ts` 的 `findSystemChrome`），其 `systemChromePaths` 在 win32 下**只搜 Google Chrome，不含 Microsoft Edge**。返回 undefined → `PRODUCER_HEADLESS_SHELL_PATH` 未设 → layer 渲染经 engine `resolveHeadlessShellPath` 回退到损坏的 managed chrome-headless-shell → 0xC000007B。
- 对比：cli 的 `studioServer.ts`（layer 分支）用 `findSystemChromium`（已含 Edge），`hyperframes preview` 命令路径正常；但 studio dev server 路径缺失 Edge 候选。
- **修复**：在 `packages/studio/vite.browser.ts` 的 `systemChromePaths` win32 分支补 Edge 候选（`Program Files`/`Program Files (x86)`/`LOCALAPPDATA` 下的 `Microsoft/Edge/Application/msedge.exe`）。验证 `findSystemChrome()` 现返回 `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`。
- 注意：studio dev server 直接跑 TS（vite），**改完重启 dev server 即生效，无需重建 dist**。而 `hyperframes preview` 走 cli 的 dist，需 `cd packages/cli && npx tsup --no-clean` 重建。

## 真正根因：`findSystemChromium` 是 async，顶部回退把 Promise 赋给了 env（2026-08-17 20:48）

- studio 的 FFmpeg/layer 导出报 `Browser was not found at the configured executablePath ([object Promise])` / `Code: 3221225595` (0xC000007B)。
- 真正的根因（之前判断错方向）：`packages/cli/src/server/studioServer.ts` 的 `findSystemChromium` 被声明为 `async function`，但体内无真正异步操作，于是**总是返回 Promise**。早期我加的「进程启动顶部设置 `PRODUCER_HEADLESS_SHELL_PATH`」写的是 `const systemChromium = findSystemChromium();`（未 await）→ 拿到 Promise，`if (systemChromium)` 对 Promise 恒为 true → 把 `"[object Promise]"` 赋给 env。后续 layer 分支的 `if (!process.env.PRODUCER_HEADLESS_SHELL_PATH)` 因 env 已为 truthy 字符串而**跳过**，于是用损坏的 Promise 路径 → 浏览器启动失败。
- **修复**：把 `findSystemChromium` 改为同步函数（去掉 `async`），顶部调用与 layer 分支（保留 `await`，对 string 是 no-op）都正确拿到 Edge 路径字符串。无需手动设 env。
- 验证：不带 `PRODUCER_HEADLESS_SHELL_PATH` 重启 preview，触发 layer 渲染，日志 `[BrowserManager] Browser launched (Edg/148.0.3967.54, ...)` 成功，无 Promise/Code 123/0xC000007B。
- 注意：改完需 `cd packages/cli && npx tsup --no-clean` 重建 dist，并**重启 preview 进程**才生效（`hyperframes preview` 用 dist/cli.js）。
- 之前对 `vite.browser.ts`（studio dev server 路径）加 Edge 候选仍有价值（dev server 路径），但用户实际用 `hyperframes preview`（cli 路径），靠 studioServer 修复覆盖。

## 修 layer 渲染进度上报卡 5%（2026-08-17 21:00）

- 现象：studio 点 "Export with FFmpeg" 后前端进度条卡在 5%，但渲染实际在跑（producer capture 帧持续推进）。
- 根因：`packages/ffmpeg-layer-renderer/src/render.ts` 的 `render-main-layer` 阶段（needsMainLayerRender 分支）在 `await renderMainLayer(...)` 期间只发了一次 `onProgress({progress:5, stage:"render-main-layer"})`，而 `renderMainLayer` → `renderHtmlToMedia` → `executeRenderJob` 没把 producer 内部的逐帧进度（captureStage 每 30 帧 updateJobStatus，job.progress 25→70）透传出来，导致该长阶段无任何进度更新。
- 修复（三处，均在 ffmpeg-layer-renderer/src）：
  1. `prerender.ts` `renderHtmlToMedia` 增加可选 `onProgress?: (progress:number)=>void`，传给 `executeRenderJob(job, projectDir, outputPath, progressSink)`，progressSink 取 `job.progress`。
  2. `prerender.ts` `renderMainLayer` 增加 `onProgress` 参数并透传给 `renderHtmlToMedia`。
  3. `render.ts` 的 render-main-layer 分支传 `(producerProgress) => onProgress({ progress: 5 + Math.round(producerProgress/100*15), stage: "render-main-layer" })`，将 producer 的 0–100 映射到 layer pipeline 的 5–20%。
- 注意：ffmpeg-layer-renderer 的 package.json main/exports 指向 `./src/index.ts`（bun 直接读 src），但 cli 的 `dist/cli.js` 通过 tsup **内联**了它的源码。所以改 src 后必须 `cd packages/cli && npx tsup --no-clean` 重建 cli/dist 才生效。已重建（21:00:28）。
- studioServer.ts 的 onProgress 已是 `state.progress = update.progress; if (update.stage) state.stage = update.stage`（正确），前端读 state。验证：3040 进程 main-layer 渲染 capture 阶段帧正常推进（170/1920），链路通。

## layer 导出偶发 "Connection lost" 根因 = 并发 worker OOM（2026-08-17）

- 现象：渲染能成功（renders 目录多次 `complete`），但偶发"导了一会连接断开" → 前端 "Connection lost. Is the render server running?"。studioServer 的 startRender 有完整 try/catch，异常会写 state.failed 并让 SSE 正常关闭；只有**整个 Node 进程崩溃**才会表现为"连接断开"（而非"渲染失败"）。
- 已加进程级 `uncaughtException`/`unhandledRejection` 处理器（studioServer.ts 顶部，打印到 stderr）——但 OOM 是系统杀进程，不抛 JS 异常，故该 handler 本次未触发，也抓不到 OOM。
- 真正根因：layer 渲染走 `renderCompositionFromHtml` → producer，`renderHtmlToMedia` 之前**未传 workers**，producer 走 `computeWorkerSizing` 的 `auto`：本机（8–16 核 / 16–32GB）会被算成 **6 个并发 Chrome 进程**（SwiftShader 软件渲染，每进程 ~1.5GB，代码注释 MEMORY_PER_WORKER_MB=1536；旧 256MB 估算低了 6 倍，曾导致 16GB 黑屏、24GB 6-worker 堆 OOM）。峰值内存 + ffmpeg 编码把浏览器/Node 进程撑爆 → 系统杀进程 → 连接断。parallelCoordinator.ts 注释里已记录 `ts=1784042064` 该 Windows render 在 capture 阶段 hard-exit，并建议 `--workers=1` 隔离。
- **修复**：`packages/ffmpeg-layer-renderer/src/prerender.ts` 的 `renderHtmlToMedia` 注入 `workers`，默认从 `process.env.HF_LAYER_WORKERS` 读取，**默认 1（串行，内存最低最稳）**；设 `HF_LAYER_WORKERS=N` 可恢复并行。改完 `cd packages/cli && npx tsup --no-clean` 重建 dist（已重建）。
- 影响面：仅 layer 渲染路径（studio Export with FFmpeg / `hyperframes preview`），不影响 studio dev server 其他渲染类型。串行比并行慢但稳定，符合 studio 稳定优先。
- 排查技巧：若仍断开，让用户把终端 `[Studio]` 红色报错或系统事件查看器里 Chrome 崩溃/OOM 记录发来，确认是否还有别的根因。
